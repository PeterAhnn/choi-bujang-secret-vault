## 제작 2 재실행 결과

제작 2 원문과 확인 문구를 먼저 제시했다. 본인 Supabase의 메타데이터를 읽기 전용으로 확인했다. public 테이블은 defense_notes뿐이고, 사용자 앱 메타데이터의 키는 provider·providers뿐이다. 조사한 DB·역할 설정 키에는 자원별 가명 사용자·기기 허용 정책이 없다. 사용자 식별값·메모 본문·비밀값은 이 조사에서 조회하지 않았다.

src/decider.mjs에 메모 자원의 정확한 경로·메서드·쿼리 없는 요청 검사와 미등록 공지 수정 거부를 추가했다. 기존 기기·추가 확인 규칙과 원래 정상 연습 요청을 보존했다. 기본 decide를 직접 검사하는 test/step-08.test.mjs를 추가했다. 소유자 정책이 연결되지 않은 메모 단건 허용은 아직 남아 있으므로 제작 2 완료로 표시하지 않는다. 현재 공지 수정은 모두 거부되며, 강사의 정상 수정 권한은 등록·검증되지 않았다.

관련 검사 11개 중 10개 통과·1개 실패다. 가상 A 읽기·수정 허용, 미등록 공지 수정 거부, 알 수 없는 경로와 기능 경로 거부, 기존 기기·추가 확인 규칙은 통과했다. 같은 메모를 요청한 가상 B의 거부 검사는 allow를 반환해 실패했다. 이 검사는 TODO가 아니라 실제 실패로 남겼다. 별도 기존 판정 연습 4개도 통과했다. 실제 A/B 배포 요청의 새 통합 검사나 운영 심판 결과로 확대하지 않는다.

### 빈칸을 채운 막힘 프롬프트

8단계 「자료마다 갈 수 있는 구역을 나눕니다」에서 제작 2를 실행했는데 기대와 달라. 기대한 결과: A 자기 메모는 허용, B의 A 메모와 일반 학생의 공지 수정은 거부되어야 합니다. 실제 화면/첫 오류: 기본 decide()의 로컬 검사에서 A 읽기·수정과 학생 공지 수정 거부는 통과했으나, B의 같은 메모 조회가 allow를 반환했습니다. 관련 검사 11개 중 10개 통과·1개 실패입니다. 비밀값을 지운 뒤 원인 후보를 두세 개 적고, 가장 가능성 높은 하나만 최소한으로 고쳐 줘. 다른 기능은 건드리지 마. 수정 뒤 직접 확인할 방법을 알려 줘.

후보는 기본 판정기의 소유자 대조 누락, 실제 정책 공급 누락, 최종 API의 소유자 조건 누락이다. 코드와 기존 검사에서 최종 API의 소유자 조건은 유지되며, 기본 판정기에는 실제 허용 관계가 없다. 필요한 것은 정확한 자원에 대해 어떤 검증된 가명 주체와 기기가 어떤 동작을 할 수 있는지 나타내는 신뢰된 정책이다. UUID 변환만이 유일한 방법이라고 단정하지 않는다. 현재 조사한 소스·설정·DB 메타데이터에는 이 정책의 실제 값과 연결 경로가 없다. 추측한 식별자·해시·첫 접근자 등록을 쓰지 않는다.

제작 3·저장점·새 배포·새 심판은 아직 미실행이다. 현재 공식 점수 36점과 9단계 잠금은 그대로이며 외부 문의는 계속 보류한다. 제작 2의 확인 문구를 만족하기 전에 다음 제작으로 넘어가거나 제출하지 않는다.
