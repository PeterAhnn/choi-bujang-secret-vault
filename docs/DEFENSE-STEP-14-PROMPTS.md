목표: 선택한 업무 앱 한 개에 대한 접근 판정과 판정 이유를 표시합니다.

수정 대상: student/extension.mjs → renderDecision

renderIdentity를 유지하고 renderDecision만 수정합니다. appId, decision, reason, checkedAt을 어디서 받는지 확인합니다.
요청 전(idle), 요청 중(loading), 판정 수신(ok), 요청 실패(error)를 먼저 구분합니다.
allow=접근 허용, deny=접근 거부, challenge=추가 인증 또는 확인 필요, unknown=판정 확인 불가로 표시하고 원래 코드값도 함께 적습니다. 알 수 없는 decision은 확인 불가로 처리합니다.
판정 이유(reason)와 판정 시각(checkedAt)을 함께 표시합니다. 오류는 안전한 error.message를 표시하고 접근 거부 판정과 구분합니다.
직접 확인할 순서
업무 앱 하나 선택 → 접근 요청 → 해당 앱의 판정·이유·시각 확인 순서로 진행합니다.
현재 계정에서 실제로 반환된 결과를 확인합니다. 네 판정 모두를 보기 위해 정책이나 인증 정보를 변경하지 않습니다.

allow는 정책상 접근 허용이라는 뜻이며 실제 앱 접속 성공을 보장하지 않습니다. challenge는 이 앱이 추가 인증을 대신 수행한다는 뜻이 아닙니다. 전체 업무 앱 권한 목록을 조회하는 기능도 아닙니다.

목표: 선택한 업무 앱 한 개에 대한 접근 판정과 판정 이유를 표시합니다.
수정 대상: student/extension.mjs → renderDecision

진행 방식:
1. 현재 구현을 읽고 유지할 기능, 수정할 함수, 입력 데이터, 확인할 상태를 먼저 설명해 줘. 파일이 없거나 계약이 다르면 추측해서 새 구조를 만들지 말고 차이를 알려 줘.
2. 아래 구현 순서에 따라 작은 단위로 수정해 줘. 각 수정 뒤 변경한 파일·함수와 이유를 짧게 설명하고, 내가 확인할 화면과 예상 결과를 알려 줘.
   1) renderIdentity를 유지하고 renderDecision만 수정합니다. appId, decision, reason, checkedAt을 어디서 받는지 확인합니다.
   2) 요청 전(idle), 요청 중(loading), 판정 수신(ok), 요청 실패(error)를 먼저 구분합니다.
   3) allow=접근 허용, deny=접근 거부, challenge=추가 인증 또는 확인 필요, unknown=판정 확인 불가로 표시하고 원래 코드값도 함께 적습니다. 알 수 없는 decision은 확인 불가로 처리합니다.
   4) 판정 이유(reason)와 판정 시각(checkedAt)을 함께 표시합니다. 오류는 안전한 error.message를 표시하고 접근 거부 판정과 구분합니다.
3. 상태 문구는 IT업계에서 쓰는 정확한 한국어로 작성해 줘. API 상태값·함수명·data-* 속성·필수 버튼 이름은 공식 계약대로 유지해. 의미를 바꾸는 의역이나 막연한 성공 안내는 쓰지 마.
4. 학생 화면을 구현하는 단계에서는 DOM을 createElement와 textContent로 작성하고, 색상뿐 아니라 텍스트로 상태를 구분해. 키보드로 조작할 수 있는 label과 버튼을 사용해. 문서 작성 단계에서는 불필요한 UI 변경을 하지 마.
5. 내가 직접 확인할 순서를 한 번에 하나씩 안내해 줘. 코드만 읽은 것, 모의 데이터로 점검한 것, 실제 화면에서 확인한 것을 구분하고 실행하지 않은 검사는 미확인으로 남겨.
   확인 1: 업무 앱 하나 선택 → 접근 요청 → 해당 앱의 판정·이유·시각 확인 순서로 진행합니다.
   확인 2: 현재 계정에서 실제로 반환된 결과를 확인합니다. 네 판정 모두를 보기 위해 정책이나 인증 정보를 변경하지 않습니다.
현재 지원 범위: allow는 정책상 접근 허용이라는 뜻이며 실제 앱 접속 성공을 보장하지 않습니다. challenge는 이 앱이 추가 인증을 대신 수행한다는 뜻이 아닙니다. 전체 업무 앱 권한 목록을 조회하는 기능도 아닙니다.

기존 학생 코드·앞 단계 기능·Git 기록을 지우거나 덮어쓰지 마. 제공 서버·public/app.js·판정 코드·인증 설정을 수정하지 마. 토큰·비밀번호·API 키를 요청하거나 출력하지 마.
수업용 AI가 명령을 실행할 수 없다면 실행했다고 말하지 말고 내가 PowerShell에서 실행할 명령과 작업 폴더를 알려 줘. 실제 유료 AI 요청·보안 조치·단계 제출은 임의로 실행하지 마.
끝나면 변경 파일, 직접 확인한 결과, 미확인 항목, 다음 작업을 정리해 줘. 커밋 해시나 통과 결과를 만들어 내지 마.

아래는 현재 단계 화면의 공식 과제 안내야. 위 보충 설명과 충돌하면 구현 전에 차이를 알려 줘.
목표: 업무 앱 접속 요청의 결과(허용·거부·추가 확인·확인 불가)와 요청 실패를 서로 다르게 보여 줍니다.

고칠 파일: renderDecision. 13단계 함수는 그대로 둡니다.

받는 값: renderDecision({ status, mode, data?, error?, appId }) - status: idle(요청 전)·loading·ok·error - data: { appId, decision, reason, checkedAt }, decision: allow·deny·challenge·unknown

상태별 표시: | 상황 | 보여 줄 것 | |---|---| | idle | 앱을 골라 접속을 요청하라는 안내 | | allow | 허용과 reason | | deny | 거부와 reason | | challenge | 추가 확인이 필요하다는 안내. 앱이 확인 절차를 대신하지 않음 | | unknown 또는 목록에 없는 값 | 확인 불가. 허용으로 보이지 않게 | | error | 요청 실패. 차단 판정이 아님 |

AI 에게 붙여 넣을 프롬프트: student/extension.mjs 의 renderDecision 만 구현해 줘. renderIdentity 는 그대로 둬. 입력은 { status, mode, data?, error?, appId } 야. data 는 { appId, decision, reason, checkedAt }. - idle 이면 앱을 골라 접속을 요청하라는 안내, loading 이면 판정을 확인하는 중이라는 것을 보여 줘(예: "앱을 골라 접속을 요청하세요", "판정 확인 중"). - 판정은 한국어 뜻과 원래 값을 함께 보여 줘: 허용(allow), 거부(deny), 추가 확인 필요(challenge), 확인 불가(unknown). reason 과 checkedAt 도 함께 적어. - unknown 이거나 이 네 값이 아니면 확인할 수 없다는 뜻과 원래 값 unknown 을 함께 보여 줘(예: "확인 불가(unknown)"). unknown 과 요청 실패 화면은 허용되었거나 정상인 것처럼 읽히면 안 돼. "허용되지 않음"처럼 부정하는 문장은 써도 돼. - status 가 error 면 요청이 실패했다는 것과 error.message 를 보여 주고, 이것이 거부 판정이 아니라는 것도 알려 줘(예: "요청 실패: " 뒤에 message). - 색만으로 구분하지 말고 글자로도 구분해. textContent 만 써.

스스로 확인: 업무 앱 하나를 선택하고 접근 요청을 누른 뒤, 해당 계정에서 실제로 반환된 판정·이유·시각을 확인합니다. 요청 실패는 접근 거부와 구분합니다. 현재 계정에 나오지 않는 네 가지 판정을 억지로 재현하거나 정책을 변경하지 않습니다. 키보드로 앱을 선택해도 결과가 갱신되는지 확인합니다.

필수 확인 항목: student-source-changed, server-decisions-distinct, decision-reason-visible, unknown-not-allow, failure-not-allow. AI가 제출한 커밋의 코드를 위 항목과 대조해 판정합니다. 실제 화면에서의 동작은 아래 안내에 따라 직접 확인합니다.
