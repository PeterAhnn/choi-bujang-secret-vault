# 12단계 실제 요청 표를 만드는 절차

학생 자료실의 실제 HTTP 검사와 운영 심판의41종 총공세를 구분한다. 결과가 없는 행은 미실행이며 과거 통과·로컬 가상 검사로 채우지 않는다.

## 기대값을 먼저 고정한다

`src/verification-results.mjs`의 VERIFICATION_CASES가1~11단계 확인 항목과 기대값을 정한다. 실측 기록은 기대값이나 통과 여부를 입력받지 않는다. 실제 상태·요청 ID·확인 시각이 모두 있고 고정 기대값과 일치할 때만 `실측 일치`로 표시한다. 운영 엔진의 추가 본인 확인·신원 회수처럼 이번 자료실에서 연결하지 않은 기능은 미실행으로 남긴다.

## 현재 커밋을 배포하고 실제 요청을 실행한다

1. Git 원격과 `/aleph.json`의 실제 커밋을 대조한다.
2. 비로그인 GET `/api/notes`, 잘못된 토큰 GET `/api/notes`, 비로그인 POST `/api/restore`, 공개 `/data.json`과 원본 DB 직접 요청을 실행한다. 응답 상태와 서버가 제공한 요청 ID·시각만 보관한다. DB 공개 키는 비공개 설정에서 읽으며 출력하지 않는다.
3. 승인된 B 화면에서 자기 메모의 `수정`을 누른 뒤 `수정 취소`를 눌러 정상 단건 조회를 확인한다. 저장하지 않는다. `백업으로 복구`는 자기 메모의 최초 사본과 같음을 확인하고 실제 복구 응답을 남긴다. 원본4건을 마지막에 다시 대조한다.
4. 같은 B 화면의 `서명 보호 확인`을 한 번 실행한다. 고정된 요청 순서는 미서명GET목록→경로를 바꾼GET단건→본문을 바꾼PUT단건→정상 서명GET목록→같은 서명GET목록 재전송이다. 기대 상태는403·403·403·200·403이다. 시험용 존재하지 않는 ID를 사용하므로 변조 시험은 기존 메모를 수정하지 않는다.

## 서버 기록과 연결한다

메모 목록·단건·복구의 기본 진입점에 관측 어댑터가 붙는다. 기존 인증·기기 서명·소유자 검사 결과는 그대로 두고 실제 JSON 응답 직전에 서버의 요청 ID·확인 시각·메서드·고정 자원 종류·상태·짧은 오류코드·헤더 존재 여부만 기록한다. 헤더 값·토큰·서명·nonce·사용자번호·메모·전체경로·쿼리·IP는 기록하지 않는다.

실행한 UI 절차의 시간 범위·순서·메서드·자원을 실제 서버 기록과 대조하고 각 응답의 요청 ID를 연결한다. 경로와 본문 변조는 같은 오류코드를 낼 수 있으므로 오류코드 하나로 시험 종류를 추정하지 않는다. 후보가 여러 개이거나 순서를 확인할 수 없으면 근거 부족으로 남긴다. 로그 중복은 요청 ID로만 제거한다.

가린 실제 결과는 `evidence/step-12-http-results.json`에 검사한 커밋과 함께 보존한다. 운영 사이트의 공식 판정과 다른 학생의 접속 기록은 이 파일에 넣지 않는다. `GET /api/operations`가 이 기록과 고정 기대값을 읽어 한 표로 반환한다. 화면은 `작전실 새로고침`으로 서버 표를 다시 읽는다. 화면 문구 자체를 시험 통과 근거로 쓰지 않는다.

## 현재 범위

현재는 관측 어댑터를 준비하는 중이며 새 실측 요청은 아직 실행하지 않았다. 빈 기록은 모두 미실행으로 표시한다. 실제 실행 후 검사한 커밋·요청 ID·확인 시각과 결과를 갱신한다. 앞 단계의 공식100점과 로컬 가상 검사 결과는 각 단계 기록에 별도로 있다.
