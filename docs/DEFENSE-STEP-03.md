## 공식 상황과 만들 방어 도구

지금 상황: 자료가 서버로 옮겨졌어도 로그인 없는 사람이 공개 API 주소를 부르면 읽을 수 있습니다. 서버가 요청자의 신원을 직접 확인해야 합니다.

만들 방어 도구: Supabase Auth로 실제 로그인과 로그아웃을 붙이고 서버가 인증 토큰을 검증합니다. 로그인한 계정의 가상 메모 추가·수정·삭제도 붙입니다. 로그인은 신원 확인일 뿐 타인 자료 접근은 4단계에서 막습니다.

공식 API 계약: POST `{id,title,body}`의 id는UUID, 생략하면 서버가 생성해 `{id}` 반환. 한 건 GET·PUT·DELETE는 `/:id`; 한 건 GET은 `{id,title,body}`. 목록 GET은 로그인 사용자의 메모 배열. 실제 학생 자료를 넣지 않는다. 소유자 차단을 이번 단계의 완료 기능으로 주장하지 않는다.

직접 확인할 것: 시크릿 창에서 로그인 없이 자료가 안 보이는가? 정상 A 로그인 뒤 가상 메모를 추가·수정·삭제할 수 있는가? 브라우저에 서버 전용 키가 없는가?

100점 받는 법: 기본 조건 모두70점, 가산 각각10점. 무로그인 목록401/403과JSON 오류(빈 화면/HTML 아님), 자동 생성 /aleph.json 열림, 첫 화면 nosniff 또는CSP 헤더. 재제출 최고점 유지.

문제 확인: 현재 첫 오류를 읽고 공식 막힘 프롬프트의 순서에 따라 원인 후보2~3개 중 하나만 최소 수정하고 직접 검증한다. 실패·자기 점검·공식 판정을 구분한다.

- 제작1 완료. 실제 배포에서 비로그인 상태·가상 잘못된 계정 실패 이유·비밀번호 칸 비움 확인. 사용자가 A를 생성했고 실제 DB 계정1개·이메일 확인1개를 확인했다. A 정상 로그인과 로그아웃 후 로그인 폼 재등장을 직접 관찰했으며 사용자가 다시 로그인 완료도 알렸다. 개인정보·비밀번호·JWT는 기록하지 않았다.
