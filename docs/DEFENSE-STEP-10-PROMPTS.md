## 실제로 있었던 사고 · 깃랩 데이터베이스 삭제와 작동하지 않던 백업

2017 · GitLab

2017년 1월 31일 깃랩 엔지니어가 복제 문제를 고치던 중 예비 서버가 아닌 운영 데이터베이스의 데이터 폴더를 실수로 지웠고, 멈추기 전까지 약 300GB가 사라졌습니다. 매일 돌던 백업은 데이터베이스 버전이 맞지 않아 조용히 실패하고 있었고, 실패 알림 메일마저 수신 거부돼 아무도 몰랐습니다. 결국 6시간 전에 우연히 떠 둔 스냅숏으로 복구했지만 약 6시간 분량의 프로젝트, 댓글, 신규 가입 계정이 사라졌습니다.

## 이 단계로 막을 수 있었던 부분

백업이 실제로 복원되는지 정기적으로 시험하고 그 결과를 기록으로 남겼다면, 백업이 몇 달째 비어 있다는 사실을 사고 전에 알아챌 수 있었던 부분입니다.

## 만들 방어 도구

침해 전에 검증한 자료와 정책 사본에서 대상만 복원합니다. 감사 기록은 보존하고 1~9단계의 정상·금지 요청을 다시 확인합니다.

## 프롬프트 순서

### 이어받기

이 폴더는 1~9단계까지 만든 같은 자료실이야. 이번에는 10단계 「백업에서 자료실을 되살립니다」를 할 거야. AGENTS.md와 README.md, 폴더 구조, git 상태, git log -1을 읽고 README의 단계 기록이 마지막 커밋과 맞는지 대조해 줘. 어긋나면 먼저 알려 줘. 현재 기능을 다섯 줄 이내로 요약하고 다른 작업은 보존해. 아직 아무 파일도 고치지 마.

### 만들기 1: 제작 1

침해 전에 검증한 안전 정책 사본과 현재 시험 정책의 차이만 보여 주는 기능을 만들어 줘. 사본이 없거나 검증 실패면 중단해. 실제 운영 정책은 건드리지 마.

확인: 복원할 버전과 변경 범위가 실행 전에 보여야 합니다.

### 만들기 2: 제작 2

검증한 안전 정책 버전으로 시험 정책을 되돌리는 절차를 붙여 줘. 다른 서비스 규칙과 감사 이력은 보존하고, 실행 전에 바뀔 항목을 확인하게 해 줘.

확인: B의 A 자료 요청은 다시 거부되고 A 정상 요청은 유지되어야 합니다.

### 만들기 3: 제작 3

비공개 가상 메모 사본에서 지정한 한 건만 복원하는 POST 경로를 붙여 줘. ID·소유자·내용 해시를 대조하고 다른 메모와 감사 기록은 보존해. 시험 계정 B의 메모로만 확인하고 서비스·경로를 README에 적어.

확인: 복구 대상 한 건의 ID·소유자·내용 해시가 사본과 같아야 합니다.

### 만들기 4: 제작 4

복구 뒤 1~9단계의 정상·금지 요청을 다시 실행할 순서를 README에 적어 줘. 실행하지 않은 시험은 미실행으로 두고 결과를 꾸미지 마.

확인: 자료와 정책이 돌아오고 이전에 막던 요청이 다시 거부되는지 볼 수 있어야 합니다.

### 제출 전 확인

이번 변경을 「10단계 저장점」으로 커밋해 줘. 그다음 npm run bundle을 실행해 제출 묶음 JSON과 요약을 보여 줘. 오류가 나면 첫 오류만 고쳐 줘.
