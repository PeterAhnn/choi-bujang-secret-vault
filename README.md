## 12단계 작전실과 검사한 버전

실제 API를 검사한 코드 커밋은 **8ac9b381625d1f5030a25442d22100c6f72977c5**이다. 가린 실제 요청12건을 반영한 커밋은 **c2a817d83c2e5e515c0d70d15b87798d18e21d24**이다. 두 커밋 사이에 `api/`·`src/`·`public/`의 실행 코드는 바뀌지 않았다. 후속 기록·안내 커밋과 검사한 코드를 구분한다. 첫 공식 제출 **b2d940aa41b784055857dae4949a1ca72ab5cc1e**는 `S12_BUNDLE_UNSUPPORTED`로0점이었다. 심판의 격리 환경에서 `node:util`을 사용할 수 없다는 판정이었다.

제출 도구는 허용된 `node:fs`를 사용하고 탐지 연습의 평면 응답을 직접 비교한다. 12단계 묶음은 공개 HTTPS GET만 실행한다. 실제 API에서 앞서 측정한 12건과 이 묶음의 자기 점검은 별도 근거이다. 이전 단계의 쓰기 검사와 실제 권한·서명·복구 정책은 유지한다. 두 번째 제출 ed0d34bf0053fb9a2e3f0c6b0286249e79586a7c도 0점이며 첫 오류가 허용 범위 밖 Git 명령으로 바뀌었다. 자기 점검의 HEAD 읽기를 공식 묶음과 같은 `git rev-parse --verify HEAD`로 맞췄다.

세 번째 제출 68fe18b5bf66f711e4aa25a64cb88d64109847c5는 53점이며 묶음 실행은 끝났으나 실행 기록 대조가 실패했다. HTTP를 보내지 않은 가상 연습 8건과 쓰기 미실행 4건은 묶음에서 `not_run`으로 구분한다. 임의 헤더와 attackId 옵션을 넣은 두 후속 제출도 53점으로 실패했다.

현재 수정은 [공식 통과 표본](https://github.com/ChoiTimo/byteback-sample-pass/blob/e94ecff31e6b7003d1ccc60d9fa943ac80c6411d/src/attack-check.mjs)의 실제 연결 방식인 `fetch(url, { alephEvidence: { caseId: attackId, requestKey: 'read' } })`를 따른다. 메타데이터는 헤더나 URL에 넣지 않는다. 표본의 stage/result 등 다른 필드는 가져오지 않고 기존 R5 묶음의 세 필드를 유지한다. 공식 규격을 적용한 로컬 검사에서 수정 전 8건의 연결 누락을 재현했다. 실제 보호 API·DB·실측 표는 유지하며, 공식 재검사 결과는 별도로 확인한다.

515b58671a1cdfb0c406c1a4ad82ad659208cd9a에서는 요청 연결이 인정됐으나 `observed`의 설명 문장이 지원되지 않아53점이었다. 12단계 묶음의 실행 결과는 실제 응답에서 읽은 `HTTP 상태번호`만 기록한다. HTTP를 실행하지 않은12항목은not_run으로 구분하고 설명·판단은별도문서에남긴다. 값은기대값이나고정성공문구로채우지않는다.

자료실의 **작전실 새로고침**은 보호된 GET `/api/operations`를 호출한다. 서버가 읽은 판정 규칙3개, 현재 승인 상태, 사용자별 기기·백업·복구 감사 수, 안전 정책 명세 버전을 보여 준다. 같은 요청 ID·시각·표 내용이 가린 서버 기록과 일치함을 확인했다. 운영 탐지 사건 입력·운영 신원 회수의 연결 상태는 미확인으로 표시한다.

실제 B 화면에서 자기 메모 단건 조회·복구와 정상 서명200, 미서명·경로 변조·본문 변조·재전송403을 확인했다. 비로그인·잘못된 토큰·직접 DB·무인증 복구는401이며 공개 JSON은200·메모0건이다. 원본 가상 메모4건의 ID·소유자·제목·본문·생성 시각이 최초 백업과 모두 같다. 실제 복구 확인 뒤 전체 복구 감사는8건이며 이전 감사도 보존한다.

## 설치와 실행

검사 환경은 Node.js24.21.0과 npm11.19이다. 의존성 버전은 package-lock.json으로 고정한다. 아래 명령은 PowerShell에서 저장소 폴더를 기준으로 실행한다.

```powershell
git clone https://github.com/PeterAhnn/choi-bujang-secret-vault.git
Set-Location choi-bujang-secret-vault
npm ci
git log -1 --oneline
```

현재 서비스의 재현 순서는 다음과 같다.

1. 기존 Vercel 프로젝트 `peter-ahns-projects/choi-bujang-secret-vault`와 연결된 저장소·커밋을 확인한다. `vercel project inspect --non-interactive`에서 같은 프로젝트가 나와야 한다.
2. 서버 환경변수 **SUPABASE_URL·SUPABASE_SECRET_KEY**가 공식 비밀 설정에 있어야 한다. 값은 채팅·코드·명령 인자·로그에 넣지 않는다. 새 환경에서는 본인이 공식 설정 화면에서 입력한다. `database/`의 SQL은 처음 구성할 때 검토할 자료이며, 이미 적용한 운영 DB에는 다시 실행하지 않는다.
3. Git 푸시 뒤 실제 `/aleph.json`의 저장소·단계·커밋·공개 운영 주소가 해당 저장점과 같은지 확인한다. 이 프로젝트는 Git 푸시로 자동 배포되는 것을 실제 확인했다.
4. 공개 자료실에서 본인이 로그인하고 기기 승인을 요청한다. 관리자가 화면 지문을 검토해 승인한 뒤 **승인 결과 확인**을 누른다. **서명 보호 확인**과 **작전실 새로고침**으로 정상·거부 요청과 결과표를 확인한다. 앱 설치는 브라우저 메뉴에서 선택할 수 있으며 기기 승인 판단은 서버 상태를 따른다.

로컬 정적 빌드는 `npm run build -- --local`로 검사한다. API를 포함한 개발 서버 명령은 `vercel dev --listen 127.0.0.1:3000`이다. 이 명령은 설치된 Vercel CLI61.1.0 도움말로 형식을 확인했으며, 프로젝트 연결·비공개 환경변수 준비 뒤 사용한다. 이번 실제 API 검증은 운영 Vercel 배포에서 수행했고 로컬 API 개발 서버 실행은 미실행이다.

판정기·탐지기 연습과 복구 사본 확인은 다음 순서로 실행한다. 앞의 두 명령은 가상 연습이며 실제 신원 회수·공식 통과와 구분한다. 현재 폴더에는 검증된 사본이 있으며 새 복제본은 `node scripts/policy-recovery.mjs prepare`로 한 번 준비한 뒤 preview를 실행한다.

```powershell

```

12단계 변경을 되돌릴 때는 현재 `git status`·`git diff`와11단계 정상 저장점 **2f67e3ab0cf7a321b1705e08178408a151e6561d**의 차이를 먼저 확인한다. 보존할 다른 변경·사라질 이번 단계 파일을 제시하고 본인 확인을 받은 뒤 이번 단계 파일만 복구한다. DB 메모·백업·감사와 다른 단계·XDR를 유지한다. 배포한 뒤 로그인·소유자·기기 서명·복구를 다시 확인한다. `reset --hard`는 사용하지 않는다.

## 10단계 실제 기능과 검증

원문: [전체 프롬프트](docs/DEFENSE-STEP-10-PROMPTS.md). 작업·실패·수정 근거: [실행 기록](docs/DEFENSE-STEP-10.md).

정책 안전 버전은 **f78dc936a3f76c309b76ee6cf7b4bed397abacdd**이다. 이 버전에서 B의 실제 정상 단건 조회·수정·삭제·복구를 확인했다. Git·SHA256 명세·Git 제외 사본6개를 다시 읽어 대조한다. 사본 누락·해시 실패면 중단한다. `node scripts/policy-recovery.mjs preview`로 버전·변경 파일·해시·미리보기ID를 먼저 표시하고, `apply 미리보기ID`는 확인한 시험 정책만 복구한다. 실제 운영 소스·다른 서비스·감사 이력은 보존한다. 이전9단계 사본도 Git 제외 별도 이름으로 보존했다.

복구 서비스는 기존 자료실의 **POST /api/restore**이고 본문은 `{"id":"메모 UUID"}`이다. 기존 로그인 검증 도우미가 확인한 소유자만 사용하며 입력 소유자·역할·추가 필드는 거부한다. 비공개 defense_note_backups에서 최초 INSERT 사본의 ID·소유자·내용 해시를 다시 대조해 한 건만 복원한다. 누락·잘못된 해시·타인·ID/소유자 충돌은 거부하고 다른 메모는 보존한다. defense_note_recovery_audit는 추가만 하며 원본 삭제 뒤에도 백업·감사를 보존한다. 응답은 id/restored/contentHash뿐이다. 서버 키는 기존 비밀 환경변수만 사용한다.

실제 B 로그인 화면에서 임시 가상 메모 추가→단건 조회→수정→복구→삭제→삭제 후404→복구를 실행했다. Vercel 기록의 GET200·PUT200·DELETE200·GET404·복구POST200과 DB의 ID·소유자·제목·내용·해시 일치를 대조했다. 임시 메모는 정리했고 원본4건의 전체 해시는 적용 전후 같다. 비공개 백업5건과 복구 감사5건은 시험 이력을 포함해 보존했다. 실제 학생 자료는 없다.

실제 DB 서비스 역할의 롤백 검사에서는 B 수정/삭제 복구·A의 B 복구 거부·소유자 충돌 거부·다른 메모/감사 보존과 사본 누락/잘못된 해시의 쓰기 전 중단을 확인했다. anon/authenticated는 원본·백업 직접 조회와 복구 RPC 실행을 할 수 없다. 기존 메모 RLS·서버 권한은 유지한다.

실제 단건 조회 회귀는 Vercel이 경로ID를 id 쿼리로 전달하는데 전체 쿼리 거부가 이를 막던 문제였다. 경로와 같은 단일id만 처리하며 다른ID·중복·추가 쿼리와 공지/기능 경로는 거부한다. 판정기·소유자 필터는 보존했다. 배포 식별은 Vercel 시스템 변수의 공개 운영 주소·실제 커밋·restoreRoute를 안내한다. 보호된 개별 배포 주소의 로그인 이동을 수정했으며 이를 공식 실패의 단독 원인이라고 단정하지 않는다.

## 저장과 제출

키·토큰·실명·원본 메모 문장을 Git과 제출 묶음에 넣지 않는다. .local·.env·bundle-notes.json·artifacts/submission.json은 Git 제외다. 공개 파일에서 제거해도 과거 공개 이력이 사라진 것은 아니다.

변경 파일·비밀값 검사를 확인한 뒤 해당 단계 저장점으로 커밋하고 배포한다. 실제 공개 주소와 커밋을 대조한 뒤 깨끗한 Git에서 `npm run bundle`을 실행한다. 묶음 생성·자기 점검과 공식 판정은 구분한다. 현재 제출 화면의 배포 주소·저장소 주소·선택 설명으로 제출하고 공식100점 뒤 다음 개방 단계로 자동 진행한다.

서버 환경변수 이름은 SUPABASE_URL·SUPABASE_SECRET_KEY이며 값은 출력하지 않는다. 비밀 입력이 필요하면 공식 설정에서 처리하며 채팅으로 받지 않는다. 되돌릴 때 다른 변경·DB 자료를 보존하고 reset --hard를 쓰지 않는다.
